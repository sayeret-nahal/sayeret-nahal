# ארכיטקטורה ומודל נתונים

## בחירת הטכנולוגיה ולמה

| רכיב | בחירה | למה |
|---|---|---|
| ממשק ושרת | Next.js 16 (App Router), React 19, TypeScript | מוצר אחד שכולל גם את הממשק וגם את צד השרת, בלי שירותים נפרדים. רוב הדפים מוצגים מהשרת, ולכן נטענים מהר גם בטלפון |
| מסד נתונים | PostgreSQL ב-Supabase, אזור פרנקפורט | Postgres הוא תקן פתוח, כך שאפשר להוציא את כל הנתונים ב-`pg_dump` ולעבור לכל ספק אחר. הרשאות ברמת השורה (RLS) נאכפות בתוך מסד הנתונים |
| התחברות | Supabase Auth: סיסמה וקוד מאפליקציית אימות (TOTP) | אימות דו-שלבי בלי עלות נוספת. הרשמה אפשרית רק לכתובות שהוזמנו |
| עיצוב | Tailwind CSS v4 עם אסימוני עיצוב (tokens) | עברית ו-RTL מלאים בעזרת מאפיינים לוגיים, וקל לתחזק |
| תאריכים עבריים | ‎@hebcal/core | חישוב נכון של יום האזכרה: אדר בשנה מעוברת, ל' חשוון/כסלו ושקיעה |
| אקסל | exceljs | ייבוא וייצוא בצד השרת, וגיליונות מימין לשמאל |

**החלטות ארכיטקטורה:**
- **אין מיקרו-שירותים ואין שרת API נפרד.** כל הלוגיקה העסקית נמצאת במקום אחד: פונקציות SQL וטריגרים, שנבדקים בבדיקות אוטומטיות. כך אותם כללים חלים גם על הממשק, גם על הייבוא וגם על הטפסים הציבוריים.
- **האפליקציה משתמשת רק במפתח הציבורי** (publishable) ובסשן של המשתמש. מפתח-העל (service role) לא נמצא בשימוש ולא נדרש. גם אם יש באג בממשק, מסד הנתונים לא יחשוף מידע שהמשתמש לא רשאי לראות.
- **טפסים ציבוריים** (לחצן "אני צריך/ה לדבר", "מודאג/ת לגבי חבר" ועדכון פרטים) עובדים רק דרך פונקציות ייעודיות שמאמתות את הקלט. יש בהן הגבלת קצב (3 לשעה לכל מספר טלפון, 40 לשעה בסך הכול) ומלכודת לבוטים. למשתמש אנונימי אין גישה ישירה לשום טבלה.

## מודל הנתונים

```
contacts ──< contact_type_links >── contact_types (לוח עזר, עם סימון רגיש)
   │
   ├── contact_care (1:1) ── care_statuses (לוח עזר: תווית, תדירות, חומרה)
   ├──< interactions        (שיחות, פגישות, הודעות, הערות)
   ├──< cases ──< case_events  (פניות ודיווחי חשש + יומן פעולות לכל פנייה)
   ├──< tasks
   ├──< donations >── campaigns
   ├──< fallen_family >── fallen   (משפחות שכולות ↔ חללים)
   └──< update_links        (קישורים אישיים לעדכון פרטים; נשמר רק hash)

staff (= auth.users) · staff_invites · cohorts · regions · events · settings
not_duplicates · import_batches · audit_log (הוספה בלבד)
```

**עקרונות:**
- **רשומה אחת לכל אדם.** סוגי הקשר נשמרים כתגיות. איחוד רשומות כפולות מעביר את כל ההיסטוריה ומשאיר את הרשומה השנייה בארכיון, עם `merged_into`.
- **מצב הקשר שמור בטבלה נפרדת** (`contact_care`). כך אפשר להסתיר אותו מתפקידים שאינם עוסקים ברווחה.
- **טלפון נשמר בפורמט בינלאומי** (‎+972…). הנרמול זהה בצד השרת (`normalize_il_phone`) ובצד הלקוח (`src/lib/phone.ts`), וזה נבדק.
- **עדכניות הפרטים:** השדות `verified_at` ו-`verified_by` (האדם עצמו או הצוות) ו-`phone_status`. התצוגה `contact_health` מחשבת את מצב הנתונים של כל רשומה.
- **הסכמה לפי מטרה:** `campaign_consent`. בנוסף נשמרים `privacy_notice_version` ו-`privacy_notice_at`, כלומר איזו הודעת פרטיות האדם ראה ומתי.
- **נתוני דוגמה** מסומנים `is_demo`. הממשק מציג לידם תגית ופס אזהרה, ודוח האימפקט מתריע עליהם.

## לוגיקה בתוך מסד הנתונים (`0003_logic.sql`)
| פונקציה או טריגר | מה עושה |
|---|---|
| `contact_after_insert` | יוצר `contact_care` לכל אדם חדש. מועד השיחה הראשונה מוגרל בתוך תקופת התדירות, כדי שהשיחות לא יגיעו כולן באותו יום |
| `care_before_update` | כשמצב הקשר משתנה למצב דחוף יותר, מקדים את השיחה הבאה |
| `log_interaction` | מתעד קשר וקובע את השיחה הבאה לפי התוצאה. "נדרש המשך טיפול" פותח משימה |
| `case_before_insert/update` + `case_after_*` | קובעים מועד יעד לפי ההגדרות, מונעים סגירה בלי תיעוד ורושמים אוטומטית שינויי אחראי ומצב |
| `case_alerts` (תצוגה) | ללא אחראי / באיחור / תקועה 7 ימים / נסגרה בלי פעולה |
| `search_contacts` | חיפוש לפי חלק מהשם, טלפון (כל פורמט), דוא"ל ומחזור, עם סובלנות לשגיאות כתיב (pg_trgm) |
| `find_duplicates`, `merge_contacts` | זיהוי כפילויות בשתי רמות ואיחוד ששומר את ההיסטוריה (מנהלים בלבד) |
| `submit_talk_request`, `submit_concern`, `get/submit_update_profile`, `create_update_link` | הטפסים הציבוריים |
| `impact_report` | מספרים מצרפיים בלבד, בלי מידע אישי, לפי שעון ישראל |
| `audit_trigger`, `log_access` | יומן פעולות: שינויים, צפייה ברשומות, ייצוא, כניסות |

## גדילה
- **בדיקת עומס:** נבדק על 3,000 רשומות דוגמה. חיפוש לוקח 17 מילישניות (ב-Postgres שרץ בתוך תהליך הבדיקה).
- **אינדקסים:** trigram על שם ועל טקסט חיפוש, ואינדקסים על מחזור, אזור, אחראי ומועד השיחה הבאה.
- **סדר גודל:** המבנה מתאים לעשרות אלפי רשומות בלי לבנות מחדש. מעבר לזה הצעד הבא הוא הגדלת שרת מסד הנתונים, לא שינוי ארכיטקטורה.
